## Assumptions

Decided on the builder's behalf (change any that are wrong):

- The toggle is additive: it is off unless the developer passes zest.toggleOptions, so existing buttons are unchanged.
- Both app-controlled (pressed) and self-managed (defaultPressed) use are supported; pressed wins if both are given.
- The check mark defaults to the start of the button when checkPosition is not given.
- If onClick fails, the toggle keeps its flipped value; apps that need otherwise control `pressed`.

## Out of scope

- A separate switch control with a sliding track and knob
- Grouping toggles into radio-like or exclusive toggle groups
- Custom on and off icons other than the check mark (developers can still use iconLeft and iconRight)
- Remembering the on/off value between page loads
- Changing the look or behaviour of buttons that do not turn on toggle mode

## Role documentation

### Analyst: requirements

ZestButton gets an optional toggle mode, like a Bold button in an editor: it stays pressed when on and returns to normal when off. When on it shows a pressed look plus a small animated check mark; the check mark can sit at the start or end of the button so icons still work. Screen readers hear 'pressed' instead of the check mark. It is additive: buttons that do not turn it on look and behave exactly as before. It is for developers who install the library and for the people who use their apps.

### Architect: design

Toggle mode is added to the existing ZestButton as an optional `zest.toggleOptions` object (pressed, defaultPressed, onPressedChange, checkPosition). Nothing is restructured. The project is flat (UI/, Styles/, __tests__/, documentation/), so this design follows that layout rather than the generic components/<Component>/ layout. A new hook, UI/hooks/useToggleState.ts, owns the on/off value: controlled when `pressed` is given, otherwise self-managed from `defaultPressed`. ZestButton gets new additive code only: the destructured toggleOptions, a new `handleToggleClick` that sits beside handleClick/handleConfirmClick, a small ToggleCheck svg component placed next to AnimatedCheckmark, and a conditional render of the check at the chosen end. The existing handlers keep their bodies; the new handler is wired into the button's onClick only when toggleOptions is present. Without toggleOptions, no aria-pressed attribute, no extra class and no extra element is rendered, so non-toggle markup is byte-identical (risk 1). The toggle check is a distinct element (its own class and a pop/draw animation, in the start/end slot and tied to the pressed state), separate from the busy/success checkmark that only appears in the left icon slot after an async action (risk 2).
