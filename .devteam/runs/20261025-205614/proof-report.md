## Assumptions

Decided on the builder's behalf (change any that are wrong):

- The setting is named styles.toggle in the provider config and zest.toggleOptions.style on a single button; exact names can be refined at design time as long as the behaviour above holds.
- A per-button override (R6) is included because a central provider without an escape hatch would force wrappers for one-off buttons.
- Developer-supplied values are used exactly as written (px allowed), because the builder asked for pixel-exact control; the library's own defaults stay in rem.
- The release is a minor, additive version bump.
- Where a size look and a variant look set the same property, the variant look wins, because the variant carries the button's colour intent; this matches the design and replaces the earlier size-over-variant wording.

## Out of scope

- Styling plain, danger, outline and other non-toggle buttons from the provider (the settings are shaped so these can be added later)
- A visual theme-builder or preview tool
- Changing the toggle's behaviour, check-mark animation or accessibility semantics already decided
- Automatic contrast checking of developer-chosen colours
- Styling the dropdown menu or the spinner

## Role documentation

### Analyst: requirements

ZestButtonConfigProvider gets one central place to set the exact look of toggle buttons for a whole app: colours, variations, sizes, hover effects and other CSS properties, separately for the off and on states and for light and dark themes. It follows the same idea as the ZestTextbox provider. Only toggle buttons (ZestButton with zest.toggleOptions) are styled in this release, but the settings are organised by button kind so plain, danger, outline and other kinds can be added later without breaking anyone. It is additive: apps that do not pass the new settings look exactly as they do today. It is for developers who install the library and wrap their app in the provider; their end users see the result.

### Architect: design

Add an optional `styles.toggle` section to ZestGlobalConfig (the existing ZestButtonConfigProvider/context), and an optional `style` field on ToggleOptions for per-button overrides. Settings are organised by button kind (`toggle` only for now) as { base state looks, `light`/`dark` theme looks, `variants.<ZestVariant>`, `sizes.<ZestSize>` }, each holding per-state looks (off, on, hoverOff, hoverOn, focus, disabled, busy) as maps of CSS property name -> value. A pure compile step sanitises the settings (R8, security NFR: property names must match /^[a-zA-Z-]+$/ or be a known custom key; values must be strings/numbers with no `;`, `{`, `}`, `<`, `url(`/`expression(`/`@import`/comment tokens, otherwise the single property is dropped) and flattens them for the button's resolved theme, variant and size. Precedence, lowest to highest: built-in CSS Module look < all-toggles look < size look < variant look < per-button look; inside each layer the theme-specific (light/dark) look beats that layer's theme-less look (R4, R5, R6). The variant look beats the size look, as the updated R4 and its assumption require, because the variant carries the colour intent. The compiled declarations are emitted once as one CSS rule per state under a generated attribute id (`[data-zest-toggle-style="<id>"]`, selector specificity raised by repeating the attribute so it beats the library's own `.solid.toggleOn:hover:not(:disabled)` rules without `!important`), so pseudo-states (hover, focus-visible, disabled, busy) work, which inline styles cannot do. Rules go into one shared, ref-counted <style> element in document.head (inserted in an effect, so Next.js server rendering and React 18/19 are unaffected; the button just gets the data attribute). Compilation is memoised per settings object (WeakMap keyed on the provider's `styles.toggle` and on the per-button `style` object) and per (theme, variant, size) key, and rule insertion is deduplicated by id, so 100 toggles under one provider do the work once, an unchanged config object does no recompute, and unmounting releases the ref count and removes unused rules. No new dependencies, no timers, no listeners; cost is one small string build per distinct (settings, theme, variant, size) and one <style> element, and bundle growth is a few KB at most. The library's own CSS is untouched (no new px), the focus indicator stays unless the developer sets a `focus` look, and aria-pressed/keyboard/check mark logic is not changed. Only the data attribute (and `data-zest-toggle-check` on the already aria-hidden check svg for check colour/size) is added to the toggle render path. Public surface grows additively through the existing `export *` lines in UI/index.ts (new types such as ZestToggleStyle and the extended ZestGlobalConfig); nothing existing is removed or changed; version gets a minor bump. Docs live in documentation/ (the project's real docs folder, which holds api, configuration, features, examples, breaking-changes, development) plus README. Changes by file: UI/ZestButtonConfigContext.ts gains optional `styles` on ZestGlobalConfig (additive field only); UI/ZestButton.tsx gains optional `style` on ToggleOptions, calls useToggleStyle and renders the data attribute only in toggle mode (behaviour, aria and classes unchanged); UI/hooks/useZestConfig.ts is NOT changed (the new hook reads the provider config directly); package.json and package-lock.json get a minor version bump only (dependencies and peerDependencies unchanged, so the build-externalization and peer-dependency tests are unaffected); new tests go only in new test files, existing tests are not edited (characterization tests of current toggle/provider behaviour are written first).
