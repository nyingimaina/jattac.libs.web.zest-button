## Role documentation

### Analyst: requirements

This is revision 2 of 3 of a larger feature (R6 to R9). ZestButton gains two opt-in options on its existing `zest` configuration object. `focusSheen` (default off) plays the split button's diagonal light streak across the whole button when the button receives keyboard focus, and `sheenTrigger` (a changing string or number) lets the host play the same streak from code, with or without focus. The effect is decorative: clipped to the button, shown on every button style and theme, one sweep per focus arrival or per trigger change, and switched off under prefers-reduced-motion. It exists so keyboard users can spot which button has focus on screens full of controls.

### Architect: design

Revision 2 extends the revision-1 focus streak on the existing ZestButton without adding a new component or dependency. An optional `sheenTrigger: string | number` joins `focusSheen` on the existing `zest` object (ZestCustomProps), so it flows through the current useZestConfig merge and provider defaultProps. A small private hook (UI/hooks/useSheenTrigger.ts) stores the mount value as a baseline and, on every later change (including a number/string type change), flips a parity flag; the button/wrapper then gains the same three existing marker classes plus a `sheenProgrammatic` marker and an odd/even class. The programmatic sweep reuses the revision-1 gradient, colour variables and `zestFocusSheenSweep` keyframes, but is drawn on each element's still-unused `::before` pseudo-element (regular: the button itself; split: the wrapper, lifted above the two segments) instead of `::after`; because it is a plain class-driven animation and not tied to `:focus-visible` or `:disabled`, it plays on an unfocused, disabled or busy button with no click/state change. Replay needs no timer, forced reflow or extra DOM: each change swaps between two identical keyframe names (`zestFocusSheenSweep` and `zestFocusSheenSweepAlt`), which restarts a finished animation in one render. Whether the sheen is in use now means `focusSheen === true || sheenTrigger !== undefined`; the existing `focusSheen`/`focusSheenSplit` marker classes (and therefore the existing colours and the existing `.focusSheenSplit .dropdownTrigger::before` mount-streak suppression) are applied for that whole set, while a new `sheenFocusOff` marker cancels only the `:focus-visible`/`:has(:focus-visible)` pseudo-element animation when `focusSheen` is false, so a trigger-only button still shows nothing on focus (R1 is preserved) and the programmatic layer is unaffected. Reduced motion is handled entirely in the existing media query, so it follows a live OS change with no JS and no override; the programmatic pseudo-element gets `content: none` there. Cost: one ref and one boolean of state per opted-in button, no listeners, timers, polling, storage or network, no work that grows with the number of buttons or with data, no new dependency and no bundle-size risk beyond a few hundred bytes of CSS/JS; the public exports and existing props are unchanged (additive optional prop only).
