## Implementation deviations from the BRS's Technical Design (discovered during implementation, not guessed)

1. **Dropped the standalone `useDropdownDisclosure` hook.** It would have been a bare `useState` wrapper with no real logic — inlined as `useState` directly in `ZestButton.tsx` instead, per "avoid speculative abstractions."
2. **`DropdownMenu.Root` explicitly set to `modal={false}`.** Radix's default (`modal: true`) applies `aria-hidden` to everything outside the menu *including the trigger button itself* while open — wrong for a split button, where the trigger must stay reachable/focusable. Not specified either way in the BRS; this is the correct choice for AC 5's "Escape closes and returns focus to the chevron."
3. **Added the `force-light`/`force-dark` theme class to `DropdownMenu.Content` directly**, not just the trigger — resolves the exact portal/theming risk flagged in the BRS's "Risks" section (Radix portals content outside the trigger's DOM subtree, so an ancestor-scoped theme override wouldn't otherwise reach it).
4. **Three jsdom polyfills added to `jest.setup.js`** (`PointerEvent`, pointer-capture methods, `scrollIntoView`) — not anticipated in the BRS; found by actually running the tests against Radix and reading its source (`node_modules/@radix-ui/react-dropdown-menu/dist/index.mjs`) to confirm the trigger opens on `pointerdown`, not `click`.
